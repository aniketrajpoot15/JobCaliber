## 1. Data Model Overview

JobCaliber uses **5 MongoDB collections** structured around the Core Product Loop (`CAPTURE → TRACK → DEBRIEF → LEARN → ACT`):

```
USER (1) ──── owns ────► (N) APPLICATION
APPLICATION (1) ── contains ──► (N) INTERVIEW_ROUND
INTERVIEW_ROUND (1) ── contains ──► (N) INTERVIEW_QUESTION
INTERVIEW_ROUND (1) ── records ──► (N) PROBLEM_LOG
USER (1) ── aggregates ──► (N) PROBLEM_LOG  [Denormalized userId for analytics performance]
```

### Collection Inventory

| # | Collection Name | Mongoose Model | Purpose | Lifecycle Stage | Defined In |
|---|---|---|---|---|---|
| 1 | `users` | `User` | User identity, auth credentials, personal thresholds | Foundation | Step 1.1 (Section 2) |
| 2 | `applications` | `Application` | Job applications tracked through pipeline stages | CAPTURE / TRACK / ACT | Step 1.2 (Section 3) |
| 3 | `interviewrounds` | `InterviewRound` | Rounds scheduled/completed per application | TRACK / DEBRIEF | **Step 1.3 (Section 4)** |
| 4 | `interviewquestions`| `InterviewQuestion`| Specific interview questions asked in a round | DEBRIEF | Step 1.4 |
| 5 | `problemlogs` | `ProblemLog` | Weakness & stumble topic tags recorded in debriefs | DEBRIEF / LEARN | Step 1.4 |

## 2. Collection Specification: `users`

The `users` collection stores user account credentials, profile settings, and system threshold preferences. It serves as the tenant boundary for all user data in JobCaliber: every child record in the system belongs directly or indirectly to a document in this collection.

### 2.1 Collection Attributes

- **Collection Name:** `users` (lowercase, plural per MongoDB conventions)
- **Mongoose Model Name:** `User` (PascalCase, singular)
- **Timestamps:** Enabled (`createdAt`, `updatedAt` managed automatically by Mongoose)
- **Optimistic Concurrency / Version Key:** `__v` enabled by default, omitted in client responses

### 2.4 Data Dictionary & Field Constraints Details

1. **`fullName`:**
   - **Type:** String
   - **Allowed Characters:** Any standard Unicode text (names with accents, spaces, hyphens).
   - **Constraints:** Minimum length 2 characters (e.g., "Bo Li"), maximum 100 characters.

2. **`email`:**
   - **Type:** String
   - **Normalization:** Must always be sanitized with `trim: true` and `lowercase: true` before validation and storage.
   - **Uniqueness:** MongoDB enforces a unique index on `email`. Duplicate emails trigger E11000 duplicate key error, converted into a friendly 400 response by backend middleware.
   - **Regex Pattern:** Standard email validation regex:
     `/^[a-zA-Z0-9.!#$%&'*+/=?^_`{|}~-]+@[a-zA-Z0-9](?:[a-zA-Z0-9-]{0,61}[a-zA-Z0-9])?(?:\.[a-zA-Z0-9](?:[a-zA-Z0-9-]{0,61}[a-zA-Z0-9])?)+$/`

3. **`passwordHash`:**
   - **Type:** String
   - **Hash Format:** Standard bcrypt hash (`$2a$12$...` or `$2b$12$...`), exactly 60 characters in length.
   - **Security Restriction:** Defined with `select: false` in Mongoose schema. Default queries (`User.findById`, `User.findOne`) will NOT return `passwordHash` unless explicitly selected with `.select('+passwordHash')` in auth controller logic.
   - **Sanitization:** Sanitized from any JSON serialization via `toJSON` transform.

4. **`targetRole`:**
   - **Type:** String
   - **Optional:** Defaults to empty string `""` upon registration.
   - **Usage:** Personalized greeting, contextual metrics, and future role-specific filtering.

5. **`staleThresholdDays`:**
   - **Type:** Number (Integer)
   - **Default:** `14` (Derived from ADR-004 research: 81% of recruiter callbacks occur within 14 days).
   - **Allowed Range:** `7` to `45` inclusive. Enforced at both Mongoose validator level and Express route validator level.
   - **Role in System:** Used dynamically by the Stale Application Engine (Feature 4) and Action Center (Feature 13) to calculate whether an application's inactivity exceeds the user's personal tolerance.

### 2.5 Mongoose Schema Reference Implementation Blueprint

This code blueprint represents the exact implementation structure to be used when writing `server/models/User.js` in Phase 2:

```javascript
// server/models/User.js (Blueprint for Phase 2)
const mongoose = require('mongoose');

const userSchema = new mongoose.Schema(
  {
    fullName: {
      type: String,
      required: [true, 'Full name is required'],
      trim: true,
      minlength: [2, 'Full name must be at least 2 characters'],
      maxlength: [100, 'Full name cannot exceed 100 characters']
    },
    email: {
      type: String,
      required: [true, 'Email is required'],
      unique: true,
      trim: true,
      lowercase: true,
      maxlength: [255, 'Email cannot exceed 255 characters'],
      match: [
        /^[a-zA-Z0-9.!#$%&'*+/=?^_`{|}~-]+@[a-zA-Z0-9](?:[a-zA-Z0-9-]{0,61}[a-zA-Z0-9])?(?:\.[a-zA-Z0-9](?:[a-zA-Z0-9-]{0,61}[a-zA-Z0-9])?)+$/,
        'Please provide a valid email address'
      ]
    },
    passwordHash: {
      type: String,
      required: [true, 'Password is required'],
      minlength: [60, 'Invalid password hash length'],
      select: false // Never return passwordHash in standard queries
    },
    targetRole: {
      type: String,
      trim: true,
      default: '',
      maxlength: [100, 'Target role cannot exceed 100 characters']
    },
    staleThresholdDays: {
      type: Number,
      required: true,
      default: 14,
      min: [7, 'Stale threshold must be at least 7 days'],
      max: [45, 'Stale threshold cannot exceed 45 days'],
      validate: {
        validator: Number.isInteger,
        message: 'Stale threshold must be an integer'
      }
    }
  },
  {
    timestamps: true,
    toJSON: {
      transform: function (doc, ret) {
        delete ret.passwordHash;
        delete ret.__v;
        return ret;
      }
    }
  }
);

// Explicit index creation
userSchema.index({ email: 1 }, { unique: true });

module.exports = mongoose.model('User', userSchema);
```

### 2.6 Multi-Layer Validation Strategy for User Data

Data integrity is validated across three defense layers:

```
[ Client Input Form ] ──► (1) Frontend Validation (UX feedback: format, length)
         │
         ▼
[ Express Router ]    ──► (2) express-validator (HTTP payload schema, sanitization)
         │
         ▼
[ Mongoose ODM ]      ──► (3) Schema Validators (DB-level safety, type-casting, constraints)
         │
         ▼
[ MongoDB Engine ]    ──► (4) Unique B-Tree Index (guaranteed duplicate prevention)
```

| Field | Layer 1: Client Validation | Layer 2: Express-Validator | Layer 3: Mongoose Schema |
|---|---|---|---|
| `fullName` | Non-empty, 2-100 chars | `body('fullName').trim().isLength({ min: 2, max: 100 })` | `minlength: 2`, `maxlength: 100`, `required: true` |
| `email` | Email input type, regex pattern | `body('email').trim().isEmail().normalizeEmail()` | `match: regex`, `lowercase: true`, `unique: true` |
| `password` (input) | Min 8 chars, 1 uppercase, 1 number | `body('password').isLength({ min: 8 })` | Converted to `passwordHash` (bcrypt salt=12) before persistence |
| `staleThresholdDays`| Number input, min 7, max 45 | `body('staleThresholdDays').optional().isInt({ min: 7, max: 45 })` | `min: 7`, `max: 45`, `validate: Number.isInteger` |

### 2.7 Security & Tenant Isolation Rules Involving User

1. **Tenant Anchor:** In all sub-collections (`applications`, `interviewrounds`, `problemlogs`), every query must filter on `userId: req.user._id` derived from the verified JWT payload. The `User` model's `_id` is the single source of truth for user data isolation.
2. **Password Secrecy:** Passwords must be hashed using `bcryptjs` with a work factor of 12 before being saved to `passwordHash`. Raw passwords must never appear in logs, error traces, or unhashed form.
3. **Information Disclosure Prevention:** The `select: false` attribute combined with the `toJSON` transform ensures that even if a developer forgets to exclude `passwordHash`, Mongoose will strip it before JSON serialization.

### 3.3 Indexes Specification

| Index Name | Keys | Options | Justification & Query Pattern |
|---|---|---|---|
| `userId_status` | `{ userId: 1, status: 1 }` | — | **Pipeline View (Kanban/Table):** `GET /api/applications?status=Applied` — Fetches all applications for a user, optionally filtered by stage. This is the most frequently executed query in the entire system. |
| `userId_companyName_roleTitle` | `{ userId: 1, companyName: 1, roleTitle: 1 }` | — | **Duplicate Detection (FR-02.7, ADR-013):** Before creating a new application, query checks if the same company + role already exists for this user within the last 60 days. Case-insensitive matching done at the application layer (`.toLowerCase()` comparison). |
| `userId_appliedDate` | `{ userId: 1, appliedDate: -1 }` | — | **Date Range Filter + Sorting (FR-05.4):** `GET /api/applications?startDate=...&endDate=...` — Filters applications by when they were submitted. Descending order (`-1`) so the most recent applications appear first by default. |
| `userId_isArchived` | `{ userId: 1, isArchived: 1 }` | — | **Active vs. Archived Filtering:** Default pipeline view filters `{ isArchived: false }`. This index ensures archived applications are excluded efficiently without scanning the entire collection. |
| `companyName_roleTitle_text` | `{ companyName: 'text', roleTitle: 'text' }` | — | **Text Search (FR-05.1):** Enables `$text: { $search: "google" }` queries for partial, case-insensitive search across company names and role titles. MongoDB text indexes tokenize and stem the field values automatically. |

#### Why These Specific Indexes?

Each index exists because a specific query pattern requires it. Without an index, MongoDB performs a **collection scan** — reading every single document to find matches. With the indexes above:

- **Pipeline view** (loaded on every page visit) → `userId_status` index
- **Duplicate check** (on every Quick-Add) → `userId_companyName_roleTitle` index
- **Date filtering** (common user action) → `userId_appliedDate` index
- **Archive filtering** (every default list query) → `userId_isArchived` index
- **Search bar** (debounced text queries) → `companyName_roleTitle_text` text index

#### Why `userId` Is the First Key in Every Compound Index

MongoDB compound indexes are **left-to-right prefix-dependent**. An index `{ userId: 1, status: 1 }` can efficiently satisfy:
- Queries filtering on `userId` alone
- Queries filtering on `userId` AND `status` together

But it **cannot** efficiently satisfy a query filtering on `status` alone (without `userId`). Since JobCaliber enforces tenant isolation (`userId` is always present in every query), placing `userId` first in every compound index guarantees every user-scoped query benefits from index acceleration.

### 3.4 Data Dictionary & Field Constraints Details

1. **`userId`:**
   - **Type:** `ObjectId` (reference to `users` collection)
   - **Population:** Can be populated with `User` document via Mongoose `.populate('userId')`, though this is rarely needed since the authenticated user's info is already available from `req.user`.
   - **Tenant Isolation:** This field is the security boundary. Every controller method must include `{ userId: req.user._id }` in its query filter. Omitting this would expose one user's applications to another.

2. **`companyName` & `roleTitle`:**
   - **Type:** String
   - **Normalization:** Both fields are trimmed on input. For duplicate detection, comparison is done case-insensitively (`.toLowerCase()`) at the application layer, not at the database level.
   - **Duplicate Detection Window:** If a document with the same `companyName` + `roleTitle` (case-insensitive) exists for the same `userId` and was created within the last 60 days, the API returns a warning (non-blocking — the user can still proceed). This prevents accidental re-entries without restricting legitimate re-applications (ADR-013).

3. **`status`:**
   - **Type:** String (strict enum)
   - **Allowed Values:** Exactly 7, defined as a constant:
     ```javascript
     const STATUS_ENUM = [
       'Saved',
       'Applied',
       'OA / Screening',
       'Interviewing',
       'Offer',
       'Rejected',
       'Ghosted'
     ];
     ```
   - **Why Fixed?** Custom statuses would fragment funnel analytics. With a fixed set, the aggregation pipeline can reliably calculate conversion rates between stages (ADR-003, ADR-012).
   - **Transition Rules:** Any status can transition to any other status (no enforced state machine in MVP). The frontend guides logical transitions, but the backend does not reject "backward" moves (e.g., moving from `Interviewing` back to `Applied`).

4. **`lastStatusUpdate`:**
   - **Type:** Date
   - **Automatic Reset:** Must be set to `Date.now` every time `status` is changed (in the controller, not via a Mongoose pre-save hook, to keep the logic explicit and testable).
   - **Stale Calculation:** The Stale Engine uses this field: `isStale = (status is 'Applied' or 'OA / Screening') AND (Date.now() - lastStatusUpdate >= user.staleThresholdDays * 86400000)`.

5. **`isStale`:**
   - **Type:** Boolean (computed, persisted)
   - **Why Persisted Instead of Virtual?** Stale status needs to be filterable (`GET /api/applications?stale=true`) and displayable in batch (Kanban cards). A virtual field would require recalculation per-document per-request. Persisting the flag allows the stale engine to update it in bulk and the query layer to filter on it efficiently.
   - **Recalculation Triggers (FR-04.2):**
     - **On-Write:** When `status` changes → recalculate `isStale` for that document
     - **On-Read:** When the application list is fetched → recalculate `isStale` for all returned documents (to catch time-based staleness that occurred since the last write)
   - **Protected Statuses (FR-04.6):** Applications in `Saved`, `Interviewing`, `Offer`, `Rejected`, or `Ghosted` are NEVER stale, regardless of `lastStatusUpdate`. Only `Applied` and `OA / Screening` can be stale.

6. **`workMode`:**
   - **Type:** String (enum with empty-string default)
   - **Why Empty String Instead of `null`?** Using `''` as the "not specified" value avoids `null` checks throughout the codebase. Mongoose enum validation includes `''` in the allowed values array, so it passes validation cleanly.

7. **`source`:**
   - **Type:** String (enum with empty-string default)
   - **Values:** `''`, `'LinkedIn'`, `'Naukri'`, `'Referral'`, `'Company Website'`, `'Indeed'`, `'AngelList'`, `'Other'`
   - **Future Use:** In V2, source analytics will calculate conversion rates per source (e.g., "LinkedIn referrals have 3x callback rate vs. cold applications"). This requires the `source` field to be a controlled enum, not free-text.

8. **`resumeVersionTag`:**
   - **Type:** String (free-text label)
   - **Why Free-Text and Not Enum?** Users create their own naming conventions ("Backend_v2", "FAANG_resume", "General_March2026"). An enum would require a separate resume management feature. The tag is simply a grouping key for the Resume Cohort Tracker.
   - **Analytics Guardrail (ADR-006):** Cohort analytics only display conversion rates when a tag has ≥ 15 applications. Below that threshold, the UI shows "Gathering Data (X/15)".

9. **`fullJobDescription`:**
   - **Type:** String (no character limit)
   - **Why No Limit?** Job descriptions vary wildly in length — from 200 words to 3000+ words. Imposing a limit would force users to truncate, defeating the snapshot purpose (FR-06.2).
   - **Storage Consideration:** Long JD text increases document size. For MVP this is acceptable. If performance becomes a concern, the JD could be moved to a separate collection with lazy loading.

10. **`isArchived`:**
    - **Type:** Boolean
    - **Why Soft-Delete?** Hard-deleting applications would corrupt funnel analytics (e.g., "I had 50 applications but only see 30"). Archiving hides the application from the active pipeline while preserving it for aggregate calculations.
    - **Query Behavior:** All default list queries include `{ isArchived: false }`. A separate "View Archived" toggle can show `{ isArchived: true }`.

### 3.6 Stale Engine Logic Specification (FR-04, ADR-004)

The Stale Application Engine is one of JobCaliber's differentiating features. It flags applications that have gone silent so the user can follow up or move on.

#### Algorithm

```
function calculateIsStale(application, userStaleThresholdDays) {
  // Step 1: Only these two statuses can be stale (FR-04.6)
  const STALEABLE_STATUSES = ['Applied', 'OA / Screening'];

  if (!STALEABLE_STATUSES.includes(application.status)) {
    return false; // Saved, Interviewing, Offer, Rejected, Ghosted → NEVER stale
  }

  // Step 2: Calculate days since last status change
  const now = new Date();
  const lastUpdate = new Date(application.lastStatusUpdate);
  const daysSinceUpdate = Math.floor((now - lastUpdate) / (1000 * 60 * 60 * 24));

  // Step 3: Compare against user's personal threshold (default: 14, range: 7-45)
  return daysSinceUpdate >= userStaleThresholdDays;
}
```

#### When To Recalculate

| Trigger | Action | Why |
|---|---|---|
| **Status Change** (on-write) | Recalculate `isStale` for the updated document | A status change resets `lastStatusUpdate` to now, so the application is no longer stale — unless it moved to another staleable status. |
| **Application List Fetch** (on-read) | Recalculate `isStale` for all returned documents | Time keeps passing. An application that was fresh yesterday might be stale today. On-read recalculation catches time-based transitions without needing a background cron job. |

### 3.7 Duplicate Detection Specification (FR-02.7, ADR-013)

#### Algorithm

```
function checkForDuplicate(userId, companyName, roleTitle) {
  const sixtyDaysAgo = new Date();
  sixtyDaysAgo.setDate(sixtyDaysAgo.getDate() - 60);

  const duplicate = await Application.findOne({
    userId: userId,
    companyName: { $regex: new RegExp('^' + escapeRegex(companyName) + '$', 'i') },
    roleTitle: { $regex: new RegExp('^' + escapeRegex(roleTitle) + '$', 'i') },
    createdAt: { $gte: sixtyDaysAgo }
  });

  return duplicate; // null = no duplicate, document = duplicate found
}
```

#### Behavior

- **Non-blocking (FR-02.8):** If a duplicate is found, the API returns a `{ warning: "..." }` alongside the created document. It does NOT prevent creation.
- **Case-insensitive:** "Google" and "google" and "GOOGLE" all match.
- **60-day window (ADR-013):** Re-applying after 60+ days is considered legitimate (new hiring cycle). Only duplicates within the last 60 days trigger a warning.

### 3.8 Security & Tenant Isolation Rules for Applications

1. **Every Query Must Include `userId`:** No controller method on the `Application` model may execute a query without `{ userId: req.user._id }`. This prevents User A from seeing, modifying, or deleting User B's applications.
2. **Archive Over Delete:** The default "delete" action sets `isArchived: true` rather than removing the document. This preserves analytics integrity.
3. **Status Enum Enforcement:** The enum validator at the Mongoose level prevents injection of invalid status values. The controller should also validate status values via `express-validator` before reaching the model layer.
4. **Input Sanitization:** `express-mongo-sanitize` strips `$` and `.` operators from all user input, preventing NoSQL injection attacks on `companyName`, `roleTitle`, and other string fields.

### 4.4 Data Dictionary & Field Constraints Details

1. **`applicationId`:**
   - **Type:** BSON ObjectId
   - **Referential Integrity:** References `_id` of the `Application` document. Must be verified for tenant ownership before creating any round (i.e. verifying that the parent application's `userId` matches `req.user._id`).
   - **Required:** Yes. An interview round cannot exist in isolation without an application.

2. **`userId`:**
   - **Type:** BSON ObjectId
   - **Denormalization Justification:** While `applicationId` already points to an application that has a `userId`, denormalizing `userId` onto `InterviewRound` guarantees that every single query on `InterviewRound` can enforce tenant isolation directly at the database index layer without requiring expensive `$lookup` joins.
   - **Immutability:** Set automatically from `req.user._id` upon creation; cannot be updated by client requests.

3. **`roundType`:**
   - **Type:** String (Enum)
   - **Allowed Values (5 Canonical Types):**
     - `'Recruiter'`: Initial phone screen or recruiter chat.
     - `'Technical'`: Coding, data structures, algorithms, or live technical assessment.
     - `'System Design'`: High-level / low-level system design and architecture.
     - `'HR'`: Behavioral, culture fit, leadership principles, or compensation discussion.
     - `'OA'`: Online assessment, Hackerrank/LeetCode link, or take-home assignment.
   - **Validation:** Strict enum validation prevents arbitrary or misspelt round categories.

4. **`scheduledDate`:**
   - **Type:** Date
   - **Timezone Handling:** Stored in MongoDB as UTC ISO 8601 timestamps. The frontend displays this in the user's local browser timezone.
   - **Temporal Role:** Used to determine whether a round is in the future (upcoming prep) or past (awaiting debrief).

5. **`selfRating`:**
   - **Type:** Number (Integer)
   - **Range:** 1 to 5 (inclusive). Represented in the UI as a 5-star rating widget.
   - **Lifecycle:** Initially `null`. It becomes mandatory when submitting the 90-second debrief (FR-08.3). A round without a completed debrief has `selfRating: null`.

6. **`debriefCompleted` & `debriefCompletedAt`:**
   - **Type:** Boolean and Date
   - **Default:** `false` and `null`.
   - **State Transition:** When the user completes the 90-Second Debrief modal, `debriefCompleted` is set to `true`, `debriefCompletedAt` is recorded, and `selfRating` is saved atomically in the same operation (FR-08.6, FR-08.7).

### 4.6 Design Decisions & Architectural Rationale

#### Separate Collection vs Embedded Subdocuments
- **Decision:** Store `interviewrounds` as a top-level collection referenced via `applicationId`, NOT as an embedded array `rounds: [...]` within `applications`.
- **Reasoning:**
  1. **Action Center Query Speed:** To query across all pending debriefs or upcoming interviews for a user, an embedded approach requires scanning and unwinding application documents. With a separate collection and compound index `{ userId: 1, debriefCompleted: 1, scheduledDate: 1 }`, the database retrieves exactly the matching rounds in a single fast index scan (O(log N)).
  2. **Child Document Stability:** Both `InterviewQuestion` and `ProblemLog` link to an interview round. Referencing top-level `InterviewRound` documents with stable `_id` values is standard and clean in MongoDB. In contrast, referencing subdocuments of subdocuments creates brittle queries and complicated aggregation pipelines.
  3. **Atomic Debrief Updates:** Completing a debrief updates the round, creates multiple question records, and creates multiple problem logs. Having distinct collections allows clear transactional or batch semantics without locking or rewriting the entire application document.

#### Denormalization of `userId`
- **Decision:** Include `userId` directly on `InterviewRound`.
- **Reasoning:** Security Rule 9 requires tenant isolation on **every** query. If `InterviewRound` only had `applicationId`, finding upcoming interviews or pending debriefs for User A would require either:
  - Fetching all of User A's application IDs first, then doing `InterviewRound.find({ applicationId: { $in: appIds } })`, or
  - Running a `$lookup` join to `applications`.
  Both approaches degrade performance as data grows. Storing `userId` on `InterviewRound` provides direct tenant isolation and enables optimal compound indexes.

### 4.7 Security & Tenant Isolation Rules for Interview Rounds

1. **Every Query Must Include `userId`:**
   ```javascript
   // ALWAYS enforce tenant isolation:
   InterviewRound.find({ userId: req.user._id, applicationId: req.params.appId });
   ```
2. **Parent Application Ownership Verification:** When creating a round via `POST /api/applications/:appId/rounds`, the controller MUST verify that the referenced `applicationId` actually belongs to `req.user._id` before saving the round:
   ```javascript
   const app = await Application.findOne({ _id: appId, userId: req.user._id });
   if (!app) {
     return res.status(404).json({ error: 'Application not found' });
   }
   ```
3. **Immutability of Ownership:** Neither `userId` nor `applicationId` may be modified via `PUT` or `PATCH` updates.
4. **Debrief Submission Atomicity:** The debrief endpoint (`POST /api/interviews/:roundId/debrief`) must verify that `round.userId.toString() === req.user._id.toString()` before modifying `debriefCompleted`, `selfRating`, or writing child questions and problem logs.
